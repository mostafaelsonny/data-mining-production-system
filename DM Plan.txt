المشروع الأول: Customer Churn Prediction
1. ما المقصود بـ Customer Churn؟
خلينا نفترض إن عندنا شركة اتصالات عندها 100,000 عميل.

الشركة بتلاحظ إن بعض العملاء بيوقفوا اشتراكاتهم وبيتحولوا لشركات منافسة.

الشركة عايزة تعرف:

مين العملاء المتوقع إنهم يتركوا الخدمة؟
إيه العوامل اللي بتخلي العميل يترك الشركة؟
هل مدة الاشتراك بتأثر؟
هل السعر المرتفع بيزود احتمالية مغادرة العميل؟
هل العملاء اللي عندهم مشاكل متكررة في الخدمة أكثر عرضة للمغادرة؟
هنا بيظهر دور الـ Machine Learning.

بدلاً من انتظار العميل حتى يترك الخدمة، بنبني Model يتوقع احتمالية مغادرته.

بمعنى آخر: إحنا بنحاول نتوقع سلوك العميل في المستقبل باستخدام المعلومات المتاحة عنه.

4. أنسب Algorithms للمشروع
مش كل Algorithms مناسبة بنفس الدرجة.

خلينا ندرس الخيارات:

A. Logistic Regression
واحدة من أشهر خوارزميات الـ Classification.

رغم وجود كلمة Regression في اسمها، فهي تستخدم في Classification.

بتحسب احتمال انتماء العميل لفئة معينة.

مثلاً:

P(Churn = Yes) = 0.85
P(Churn = No) = 0.15
لو الاحتمال أعلى من Threshold معين، بنصنف العميل على إنه معرض للمغادرة.

مميزاتها:

سهلة الفهم.
سريعة.
مناسبة كبداية.
قابلة للتفسير نسبياً.
عيوبها:

قد لا تتعامل بكفاءة مع العلاقات المعقدة بين Features.
B. Decision Tree
بتشتغل عن طريق مجموعة من الأسئلة والقرارات.

مثلاً:

Is Tenure < 6 months?
       |
      Yes
       |
Is Monthly Charges > 80?
       |
      Yes
       |
High Churn Risk
مميزاتها:

سهلة الفهم والشرح.
بتتعامل مع العلاقات غير الخطية.
ممكن نعرض طريقة اتخاذ القرار بصرياً.
C. Random Forest
دي من أقوى الاختيارات للمشروع.

بدلاً من الاعتماد على Decision Tree واحدة، بنبني مجموعة من الأشجار.

كل شجرة بتعمل Prediction، وبعد كده بنجمع النتائج للوصول إلى القرار النهائي.

مميزاتها:

أداء جيد على البيانات الجدولية.
بتقلل مشكلة Overfitting مقارنة بشجرة واحدة في حالات كثيرة.
بتتعامل مع العلاقات المعقدة.
ممكن نستخدمها لمعرفة أهمية كل Feature.
D. XGBoost
خوارزمية Gradient Boosting بتبني مجموعة من الأشجار بشكل متتابع.

كل مرحلة بتحاول تحسين الأخطاء التي ارتكبتها المراحل السابقة.

مميزاتها:

قوية جداً على Tabular Data.
غالباً بتقدم نتائج تنافسية.
فيها إمكانيات كثيرة للتحكم في التدريب.
عيوبها:

محتاجة Tuning.
تفسيرها أصعب من Logistic Regression وDecision Tree.
ترشيحي للمشروع
أنصح بالتالي:

Algorithm	الاستخدام
Logistic Regression	Baseline Model
Decision Tree	Model للمقارنة والتفسير
Random Forest	Main Model
XGBoost	Advanced Comparison
مش لازم نستخدم الأربعة، لكن وجود مقارنة بين 2 أو 3 Models هيكون مفيد جداً.

والاختيار النهائي لازم يعتمد على نتائج الـ Validation، مش على شهرة الخوارزمية.

6. Preprocessing الخاص بالـ Classification
دي من أهم مراحل المشروع، وخلينا نفهم كل خطوة.

1. Remove Duplicates
لو فيه صفوف مكررة، لازم نتعامل معاها.

مثلاً:

Customer ID	Age	Churn
1001	25	Yes
1001	25	Yes
وجود بيانات مكررة ممكن يأثر على نتائج التدريب.

لكن لازم نراجع سبب التكرار قبل الحذف، لأن تكرار العميل في بيانات زمنية مختلفة قد يكون صحيحاً.

2. Handling Missing Values
ممكن يكون فيه بيانات ناقصة.

مثلاً:

Customer	Age	Monthly Charges
A	25	100
B	NaN	150
C	35	NaN
عندنا حلول مختلفة:

Mean Imputation.
Median Imputation.
Mode Imputation.
حذف الصفوف في حالات مناسبة.
اختيار الطريقة بيعتمد على نوع البيانات وتوزيعها وسبب فقدانها.

3. Encoding
الـ Machine Learning Algorithms غالباً محتاجة بيانات رقمية.

لكن عندنا بيانات نصية مثل:

Contract = Monthly
Contract = Yearly
Contract = Two Years
هنحولها لأرقام باستخدام:

One-Hot Encoding.
Ordinal Encoding عند وجود ترتيب حقيقي.
Binary Encoding في الحالات المناسبة.
بالنسبة لـ Churn نفسه:

Yes = 1
No = 0
4. Feature Scaling
بعض الخوارزميات بتتأثر باختلاف مقاييس البيانات.

مثلاً:

Age = 25
Monthly Charges = 5000
Tenure = 12
ممكن نستخدم:

StandardScaler.
MinMaxScaler.
لكن مش كل Algorithms محتاجة Scaling.

مثلاً Random Forest وDecision Tree مش محتاجين Scaling عادةً.

5. Handling Imbalanced Data
دي نقطة مهمة جداً.

تخيل إن عندنا:

90% من العملاء بيستمروا.
10% فقط بيتركوا الشركة.
لو عملنا Model بيتوقع إن كل العملاء هيستمروا، ممكن يحقق Accuracy = 90%.

لكن في الحقيقة هو فشل تماماً في اكتشاف العملاء اللي هيتركوا الخدمة!

عشان كده لازم نتعامل مع Imbalanced Data.

الحلول:

Class Weights.
Random Oversampling.
Random Undersampling.
SMOTE.
مهم جداً: أي عملية Resampling لازم تحصل على Training Data فقط، وليس قبل تقسيم البيانات؛ لتجنب Data Leakage.

60

7. Evaluation Metrics
الملف طالب:

Accuracy.
Precision.
Recall.
F1-Score.
Confusion Matrix.
ROC-AUC.
خلينا نفهمهم.

Accuracy
نسبة التوقعات الصحيحة من إجمالي التوقعات.

مثلاً لو توقعنا 100 عميل صح من أصل 120:

Accuracy = 83.33%.

Precision
من كل العملاء اللي الـ Model قال إنهم هيتركوا الشركة، كام واحد فعلاً تركها؟

Precision مهم لما تكون تكلفة التدخل مع العملاء الذين لن يتركوا الشركة مرتفعة.

Recall
من كل العملاء اللي فعلاً تركوا الشركة، كام واحد قدرنا نكتشفه؟

ودي مهمة جداً في Churn Prediction.

لأن الشركة عايزة تكتشف أكبر عدد ممكن من العملاء المعرضين للمغادرة.

F1-Score
مقياس بيجمع بين Precision و Recall.

مفيد خصوصاً لما تكون البيانات Imbalanced.

Confusion Matrix
بتوضح:

Predicted Stay	Predicted Churn
Actual Stay	TN	FP
Actual Churn	FN	TP
ومن خلالها بنعرف نوع الأخطاء اللي الـ Model بيعملها.

ROC-AUC
بتقيس قدرة الـ Model على التمييز بين الفئتين عبر Thresholds مختلفة.

كلما اقتربت من 1 كان التمييز أفضل عموماً.

ملحوظة مهمة: مش هنختار الـ Model بناءً على Accuracy فقط. لازم نراعي Recall وPrecision وF1، ونحدد الأولوية حسب طبيعة المشكلة.

4. Algorithms الخاصة بـ Association Rules
فيه 3 Algorithms أساسية لازم نعرفهم.

A. Apriori Algorithm
من أشهر الخوارزميات المستخدمة في Market Basket Analysis.

فكرتها إنها بتكتشف مجموعات المنتجات المتكررة.

مثلاً:

Frequent 1-itemsets:

{Milk}
{Bread}
{Butter}
بعد كده تبدأ تبحث عن المجموعات الثنائية:

Frequent 2-itemsets:

{Milk, Bread}
{Bread, Butter}
وبعدها المجموعات الأكبر:

Frequent 3-itemsets:

{Milk, Bread, Butter}
لكن مش كل مجموعة بتكون Frequent.

لازم تحقق الحد الأدنى من Support.

ميزة Apriori إنها سهلة الفهم والشرح، وده مناسب جداً للمشروع الأكاديمي.

عيبها إن الأداء ممكن يتأثر مع البيانات الكبيرة بسبب عدد عمليات البحث والتوليد.

B. FP-Growth
اختصار لـ Frequent Pattern Growth.

بتستخدم هيكل بيانات اسمه FP-Tree لاكتشاف Frequent Itemsets.

بدلاً من توليد كل المجموعات المرشحة بالطريقة التقليدية في Apriori، بتضغط البيانات وتستخرج الأنماط المتكررة.

مميزاتها:

أسرع غالباً مع Datasets الكبيرة.
بتقلل عمليات توليد Candidate Itemsets.
C. ECLAT
بتستخدم فكرة Vertical Data Representation.

بدلاً من تخزين كل Transaction وما تحتويه فقط، بنخزن لكل Item المعاملات اللي ظهر فيها.

مثلاً:

Milk  = {T1, T2, T4}
Bread = {T1, T2, T3, T4}
ومن خلال تقاطع المجموعات نقدر نحسب Support.

ترشيحي
استخدموا:

Apriori كخوارزمية أساسية.
FP-Growth للمقارنة إذا كان حجم البيانات مناسباً.
مش محتاجين ننفذ الخوارزميتين من الصفر؛ ممكن نستخدم مكتبة متخصصة ونشرح طريقة عمل الخوارزمية.

النظام يبحث عن Rules التي تحتوي على Milk في الـ Antecedent، ويعرض Bread كاقتراح.

2. Butter

الاقتراحات دي لازم تكون مبنية على القواعد المستخرجة فعلياً.

كمان لازم نراعي:

عدم اقتراح منتج موجود بالفعل في السلة.

إمكانية وجود أكثر من قاعدة لنفس المنتج.
عدم إظهار توصيات ضعيفة لمجرد أنها اجتازت Support فقط.
وبكده نكون بنينا نظام Recommendation بسيط مبني على Association Rules، وهو متوافق مع طبيعة المطلوب.

Regression: Energy Consumption Prediction.

Association Rules: Product Recommendation System.

Your role is to coordinate the team, establish the project architecture, review the delivered work, ensure consistency between components, build the Streamlit application, and verify that the final project satisfies the academic requirements.

You are not expected to implement every algorithm yourself. Your responsibility is to understand the overall workflow, evaluate the technical decisions, identify mistakes, and ensure that the final system works correctly.

2. Your Main Responsibilities
Your responsibilities are divided into seven main areas:

Responsibility	Description
Project Management	Plan tasks, assign responsibilities, monitor progress, and manage deadlines.
Architecture & Repository	Establish the folder structure, Git workflow, and integration contracts.
Code Review	Review team members' code before merging it into the development branch.
Integration	Connect the three Data Mining tasks into one unified application.
Streamlit Development	Build the interface through which users can interact with the three tasks.
Testing & Validation	Verify preprocessing, predictions, evaluation metrics, and application behavior.
Final Documentation	Prepare the README, project explanation, presentation, and final checklist.

Suggested public interface:

def recommend_products(selected_products, top_n=5):
    """
    Receives a list of selected products

Example:

    "Product A",
    "Product B"

Important: The Association Rules task is not a traditional supervised learning problem. Do not force it into a classification or regression pipeline. 5. Phase Three — Code Review
You are responsible for reviewing every Pull Request before it gets merged into develop.

Your review should cover five levels.

5.1. Code Structure
Check:

Is the code organized into appropriate files?

Are functions reusable?

Are variable and function names understandable?

Is there unnecessary duplicated code?

Are notebook experiments separated from the final implementation?

5.2. Data Preprocessing
This is especially important because preprocessing mistakes can make the model evaluation unreliable.

Verify:

Missing values are handled correctly.

Duplicate records are investigated and handled.

Categorical features are encoded appropriately.

Independent variables and target variables are separated correctly.

Feature scaling is applied when appropriate.

Outliers are investigated rather than automatically deleted.

Feature selection is justified.

Class imbalance is checked before choosing a treatment.

Critical: Data Leakage
Make sure the team follows this order:

Original Dataset
       |
       v
Train/Test Split
       |
       v
Fit Preprocessing on Training Data
       |
       v
Transform Training Data
       |
       v
Transform Test Data
       |
       v
Train Model
       |
       v
Evaluate Model
Never allow the team to fit the scaler, imputer, encoder, or feature selector on the complete dataset before splitting.

For oversampling or SMOTE, the operation must happen only on the training data, preferably inside an appropriate imbalanced-learn Pipeline.

5.3. Model Implementation
Check:

Are the selected algorithms appropriate for the task?

Is the model trained using the correct features?

Is the target variable correct?

Are predictions generated from unseen test data?

Are multiple algorithms compared fairly?

Are the model parameters and random seeds documented where appropriate?

5.4. Evaluation
Verify that the metrics match the task.

Task	Required Evaluation
Classification	Accuracy, Precision, Recall, F1-Score, Confusion Matrix, ROC-AUC
Regression	MSE or RMSE, R² Score
Association Rules	Support, Confidence, Lift
Do not accept a model merely because its accuracy or R² is high.

You must understand how the results were obtained and whether the evaluation method is valid.

5.5. Visualization
Make sure each task includes visualizations that actually explain its results.

Examples:

ROC Curve.

Model comparison.

Regression

Target distribution.

Correlation heatmap.

Actual vs Predicted.

Residual plot.

Model comparison.

Association Rules

Top frequent itemsets.

Support vs Confidence.

Support vs Lift.

Top association rules.

The application should contain four main sections:

Project title.

Navigation to each task.

The user should be able to:

Enter customer information.

Submit the input.

Receive a prediction.

View the predicted class.

View churn probability.

Explore the model evaluation results.

Your application must:

Use the actual prediction/recommendation functions.

Handle invalid inputs.

streamlit run app/app.py

Your most important review skill is not memorizing every algorithm. It is being able to ask:

Why did you choose this algorithm?

Why did you apply this preprocessing step?

How did you avoid data leakage?

Why is this evaluation metric appropriate?

What does this result actually mean?

Can the model predict a new observation?

Can we reproduce the same result?

If you can answer these questions and verify the implementation, you are performing your leadership role correctly.

13. Common Mistakes You Must Prevent
Allowing members to work without agreed interfaces.

Merging code without reviewing it.

Treating notebook execution as proof that the final application works.

Fitting preprocessing transformations before the train/test split.

Applying SMOTE to the entire dataset.

Using random splitting for time-dependent forecasting without justification.

Treating Association Rules as a supervised classification problem.

Displaying hardcoded predictions in Streamlit.

Comparing models using inconsistent datasets or evaluation procedures.

Leaving integration until the last few days.

Saving model artifacts without documenting how to load them.

Writing results in the README before verifying the actual experiments.
